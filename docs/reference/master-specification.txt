SONDA monitors log files.
However, SONDA should not treat every log line independently.
Each monitored application receives a Log Profile configured by the user.
The profile teaches SONDA:
-  Where the logs are located 
-  How an Application Run Cycle starts 
-  How an Application Run Cycle ends 
-  How successful cycles are identified 
-  How failed cycles are identified 
-  How individual orders/transactions begin 
-  How orders/transactions end 
-  How orders are identified 
-  What different error messages mean 
-  Which messages should be treated as Error, Warning, or Ignore 
-  How multiple log lines should be grouped together 
SONDA therefore becomes a configurable interpretation engine for logs.
Every monitored log/application must have its own Profile.
Applications do NOT all behave the same.
For example:
-  CAM may have one run-cycle format. 
-  UNITELLER may have another. 
-  DIGICEL may use different text. 
-  TERRAPAY may use another structure entirely. 
The user must configure each profile independently.
A profile should conceptually contain:
Basic application information.
Examples:
-  Application name 
-  Description 
-  Enabled/disabled 
-  Profile identifier 
Defines where SONDA should find the logs.
A profile may eventually support one or multiple paths.
Defines how SONDA recognizes the execution cycle of the application.
Defines how SONDA reconstructs a complete transaction/order from multiple log entries.
Defines patterns SONDA should recognize and how they should be categorized.
Configuration related to failures, incomplete runs, and monitoring behavior.
The configuration UI should make this understandable without requiring the user to be a programmer.
Advanced pattern/regex support may exist, but common configuration should be possible through a simple interface.
The File Location configuration tells SONDA where the logs for an application are stored.
SONDA uses these paths to continuously monitor/read the appropriate logs.
Each profile owns its own file-location configuration.
Do not assume all logs exist in one directory.
Architect this so multiple file locations can eventually be supported by one profile if needed.
This concept is extremely important.
The applications SONDA monitors are not constantly executing.
Instead, an application may run:
-  every few seconds, 
-  every few minutes, 
-  or according to another recurring process. 
One complete execution is called an:
Application Run Cycle
For example, logs might contain patterns conceptually similar to:
Application starts
 → performs work
 → processes transactions
 → finishes
The exact text used to determine the beginning/end/result of a cycle is configured by the user for each Profile.
Do NOT hardcode specific phrases.
A profile should allow configuration such as:
Application Run Start:
-  Pattern A 
-  OR Pattern B 
-  OR regex 
Application Run Success:
-  Pattern A 
-  OR Pattern B 
Application Run Failure:
-  Pattern A 
-  OR Pattern B 
Multiple alternatives must be supported.
Application errors are valid in the context of the current Application Run Cycle.
Example:
Cycle #105:
 Application fails.
SONDA creates an error.
The incident becomes:
Severity:
 Error
Status:
 Active
Then Cycle #106 runs successfully.
At that moment, the previous application error is no longer currently affecting the application.
SONDA must automatically change the previous incident to:
Resolved
It must NOT delete the incident.
Historical incidents are important.
Therefore:
Failed Application Cycle
 → Active Error
then:
Next Successful Application Cycle
 → previous error becomes Resolved
The incident remains available in historical data.
SONDA has three detection classifications:
An application-level failure or configured condition requiring immediate attention.
Typical meaning:
Immediate attention may be required.
An individual order/transaction failed or another configured condition occurred, while the application itself may still be operating.
Typical meaning:
Attention may be needed soon.
A log pattern that SONDA intentionally recognizes but should not treat as an incident.
Ignored patterns should not negatively affect System Health.
Users configure these classifications.
SONDA must NOT assume that every message containing words such as "error" is an Error.
The user teaches SONDA which patterns mean what.
For example, a profile might contain:
Pattern:
 Error obtaining exchange rate
Classification:
 Warning
or:
Pattern:
 Database connection unavailable
Classification:
 Error
or:
Pattern:
 Retrying connection
Classification:
 Ignore
The classification engine should therefore be configuration-driven.
Every important detection rule should be capable of containing multiple alternatives.
Example:
Match ANY:
- "Finding order" 
- "Searching order" 
- "Processing transaction" 
-  regex pattern 
SONDA should interpret these alternatives as logical OR conditions.
The same concept applies to:
-  Run Begin 
-  Run End 
-  Success 
-  Failure 
-  Errors 
-  Warnings 
-  Ignore patterns 
Design the internal data model accordingly.
Do not build the system assuming each rule contains only one string.
A major SONDA feature is Order Log Piling / Order Grouping.
A single business transaction may generate many log lines.
SONDA should not force the user to investigate each line individually.
Instead, SONDA reconstructs those lines into an:
Order Run
For example:
Finding order #93822
 Connecting to payer
 Getting exchange rate
 Sending request
 Receiving response
 Order sent successfully
These entries should be treated as one logical transaction.
The profile configuration must define how SONDA identifies an order.
Examples might include:
-  Order ID 
-  Transaction ID 
-  Reference ID 
-  Confirmation ID 
-  another configured identifier 
Do not assume the field is always called Order ID.
The user defines the grouping identifier.
Conceptually:
Group By: TransactionID
SONDA uses that identifier to associate log entries belonging to the same transaction.
Each Profile can define:
The pattern(s) indicating that an order/transaction started.
Example:
Finding order
The pattern(s) indicating that an order completed successfully.
Example:
Order sent
Pattern(s) indicating that the transaction failed.
Example:
Unable to send order
Defines how related log entries are matched together.
Example:
Transaction ID
These are configured manually by the user.
An Order Run has a detection result.
Use the following conceptual results:
-  Success 
-  Failure 
-  Undefined 
These are different from incident workflow statuses.
Do NOT mix them.
If SONDA detects:
Run Begin
 → related logs
 → Success condition
the Order Run is:
Success
It should count as successful for System Health.
If SONDA detects:
Run Begin
 → related logs
 → configured Failure condition
the Order Run is:
Failure
Normally this generates a:
Warning
because an individual transaction failed while the application may still be functioning.
The specific classification can also be influenced by configured detection rules where appropriate.
If SONDA finds an Order Run beginning but never discovers either:
-  a valid success condition 
-  OR a valid failure condition 
then the Order Run becomes:
Undefined
This should appear in the Error Logs / incident system.
Important:
Undefined is NOT an incident workflow status.
Keep these concepts separate.
Example:
Detection Result:
 Undefined
Severity:
 Warning or Error according to configured rules
Incident Status:
 Active
This architecture must remain separate throughout the system.

Incident workflow status has exactly these primary states:
The problem currently exists.
A user has acknowledged the incident and is investigating it.
The condition no longer exists or the user has resolved it.
These are workflow states.

-  Error 
-  Warning 
-  Success 
-  Failure 
-  Undefined 
Those describe severity or detection results.
Maintain strict separation between these concepts.
-  Error 
-  Warning 
-  Ignore 
-  Success 
-  Failure 
-  Undefined 
-  Active 
-  Investigating 
-  Resolved 
These should NOT be collapsed into a single database field.
The database architecture should reflect this distinction.
The Home dashboard contains a:
System Health
percentage.
System Health represents TODAY ONLY.
The calculation resets logically with each new day.
It uses:
-  Order Runs 
-  Application Run Cycles 
from today.
Warnings and Errors are considered equally unsuccessful for the health calculation.
The basic formula is:
Successful evaluated runs / Total evaluated runs × 100
For example:
1,000 successful runs
 20 warning/failing runs
 5 error application cycles
Total evaluated:
1,025
Successful:
1,000
System Health:
1000 / 1025 × 100
≈ 97.56%
Display appropriately rounded.
Warnings and Errors both count as unsuccessful.
Ignore rules do not count negatively toward health.
Architect the calculation so it can later support different periods even though the Home page currently uses Today.
