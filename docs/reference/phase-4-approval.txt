Implement the proposal exactly around these principles:
1. Checkpoint safety
A durable file checkpoint must never exceed the longest contiguous byte range whose raw evidence, processing receipt, interpretation effects and checkpoint advancement have committed successfully.
Reading ahead is not checkpoint advancement.
Observed file length is not checkpoint advancement.
A volatile buffer is not checkpoint advancement.
2. At-least-once acquisition, exactly-once interpretation effects
File records may be reread after crashes or retries.
Existing durable identities and processing receipts must guarantee that rereading committed bytes does not duplicate:
-  Application Runs 
-  Order Runs 
-  Incidents 
-  Occurrences 
-  Recoveries 
-  metric contributions 
-  Logs Today 
3. Stable physical evidence identity
Physical record identity must derive from the source/file generation and byte position, never from log text, current path, modification time, line number or Profile Version.
Two identical legitimate lines at different offsets remain separate evidence.
4. File path is not file identity
Rotation, renames, recreation, truncation and aliases must use the approved file-object/generation model.
Never attach an old checkpoint to a new file merely because the pathname is identical.
5. Ambiguous rotation must fail safe
If SONDA cannot prove continuity or determine what happened to unread bytes, create an operational gap/identity uncertainty condition.
Do not skip bytes and do not claim source completeness.
6. Partial records
Do not interpret or checkpoint an incomplete physical record.
Preserve exact byte offsets across:
-  UTF-8 multibyte characters 
-  UTF-16 code units 
-  split CRLF 
-  split BOM 
-  partial final writes 
7. Source failures are not business failures
Missing files, unavailable UNC shares, access denied, reader failures, encoding failures or database outages must never fabricate an Application Failure or business Error.
Feed them into operational/source availability state.
8. No unsafe deadline inference
EOF, quiet time, wall-clock elapsed time, file age, latest timestamp, successful empty read and a caught-up byte offset do not by themselves prove semantic completeness.
Default production completeness remains None.
Without a validated completeness contract, report deadline evaluation as deferred rather than generating a false timeout.
9. Deadline scheduler
The production scheduler must submit the existing deterministic AdvanceTime command only after a valid durable completeness certificate exists.
The scheduler callback itself must not contain business outcome logic.
10. Worker ownership
Maintain one fenced active ingestion owner per Application.
A stale worker may finish an operating-system read but must be incapable of committing evidence, advancing a checkpoint or issuing a deadline command after its fence is lost.
11. Backlog
Processing after downtime must resume from durable checkpoints and remain bounded.
Do not reset to EOF, silently discard history, or use an unbounded memory queue.
12. Profile behavior
Do not add a second interpretation engine.
File acquisition feeds the already accepted Domain/Application/PostgreSQL pipeline.
Existing Profile version pinning, retry behavior, incident resolution, System Health and Logs Today rules remain authoritative.
