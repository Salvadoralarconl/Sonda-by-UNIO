# Phase 2 proposed schema and EF Core mappings

Status: **implemented design; stopped for user review**. Parent scope: [Phase 2](phase-2-scope.md). Atomic behavior: [transactions](phase-2-transactions.md). This is the design specification; the [implementation review](../phase-2-review.md) identifies concrete storage representations and limitations.

## Conventions and ownership

Use schema `sonda`. Team/Application/Profile IDs preserve existing domain strings as PostgreSQL `text COLLATE "C"`; technical session/evidence/version/receipt IDs use `uuid`. Domain run/incident/occurrence IDs remain text rather than being replaced with unrelated UUIDs. Every domain key is qualified by team and processing session in storage. IDs have ordinal, case-sensitive semantics with no trimming, numeric coercion, or case folding.

Below, `T` means `team_id`; `S` means `session_id`; `P` means `profile_id`. Composite primary/alternate keys and composite foreign keys include ownership, even where a UUID is globally unique. All rows ultimately reference their Team; session-scoped rows reference `(T,S)`. Profile ownership includes Application; version/source/run FKs must prove the same Application/Profile, not just separately valid IDs. Use `ON DELETE RESTRICT` for historical/configuration/evidence relationships. No retention purge is implemented.

Use text enums with CHECKs, `integer` for Phase 1 cycle/attempt/evidence-line numbers, `bigint` for receipt sequence/revisions, `timestamptz` for UTC instants, `date` for explicit reporting buckets, `bytea` for exact snapshots/content hashes, and `jsonb` for nonidentity structured payloads. UUIDs are generated by the adapter. Guard counter overflow rather than wrapping. EF maps `DateTimeOffset` normalized to UTC and `DateOnly`; timezone IDs are stored separately. For exact .NET tick round trips, retain companion UTC tick values on engine timestamp fields; PostgreSQL timestamp columns are query/audit representations at database precision. Constraints check tick/timestamp agreement within that precision. Do not silently change midnight classification through rounding.

`IEntityTypeConfiguration<T>` mappings explicitly declare tables, composite keys/FKs, conversions, required fields, checks, indexes and restricted deletes. SQL migrations supply triggers/deferred constraints that EF cannot express. Storage entities are separate from mutable engine classes. No lazy-loading proxies, EF navigation inside Domain, or cascade replacing aggregate graphs.

| `reporting_contexts` | T, context UUID, server timezone ID and resolved rules snapshot/hash, effective time, policy version | Immutable; derives from monitoring server timezone, never browser preference |

Publication is a single transaction: validate, check complete applicable simulation provenance, construct the exact snapshot, insert version and its normalized rules/patterns/source settings, seal it. Snapshot bytes are authoritative; normalized rule rows are immutable inspection data. A deferred database consistency trigger compares the normalized children to the stored typed JSON representation at sealing and prevents subsequent changes. Never reserialize `jsonb` and call it the original snapshot. Store a snapshot hash plus exact bytes; the hash is an integrity check, not a substitute for content.

Parsing and identifier configuration children are included in that sealing check. The exact snapshot remains authoritative; these explicit queryable mappings do not introduce a second editable configuration. Draft validation/publication and activation concurrency follow the lifecycle in the transaction proposal. Mutable Application, Profile and Log Source metadata carry bigint revisions; `profile_runtime` also carries a distinct activation revision.

Reject UPDATE/DELETE and later child INSERT on sealed versions with database triggers; restricted application role cannot disable them. A draft edit does not edit a version or reuse its number. Validator/simulator, not SQL, proves parsing/regex validity and warns about pattern overlap. Database shape checks do not claim to decide arbitrary regex intersection.

## Inputs, interpretation and runtime

| Table | Columns and relationships | Key/invariants |
| --- | --- | --- |
| `application_runtime` | T,S, application ID, revision, next input sequence, last processing ticks, current reporting context | PK `(T,S,application_id)`; row lock serializes all Profile lanes for one application |
| `profile_runtime` | T,S,P, active version ID, cycle counter, ID allocator counter, open application run ID?, blocked diagnostic?, last receipt ID, checkpoint format/version/hash | PK `(T,S,P)`; exact persisted state and active version; optional checkpoint cache is rebuildable |
| `raw_evidence` | T,S, evidence UUID, source ID, supplied source-generation token and ordinal, original payload bytes/text, payload hash, optional path/encoding/byte-range metadata, captured timestamp | UNIQUE `(T,S,source_id,generation_token,source_ordinal)`; same message at different positions is different evidence; nullable file metadata makes no claim of production capture |
| `processing_receipts` | T,S, receipt UUID, application ID, P, request ID, input sequence, stable evidence-line number, evidence ID, bound version ID, exact request fingerprint, outcome Applied/Rejected, diagnostics/result bytes, processing timestamp/ticks, recorded time, transaction ID | UNIQUE `(T,S,request_id)`, `(T,S,application_id,input_sequence)`, `(T,S,evidence_id)` and `(T,S,evidence_line)`; version/engine recorded even for rejection |
| `entry_interpretations` | T,S, receipt ID, parsed event timestamp/ticks, timestamp quality, message, identifier, fields, rule matches/winners/suppressed matches, typed effects/proof, diagnostic trace | PK receipt; durable parse/match provenance; raw evidence does not acquire business severity merely because it contains an error word |
| `commit_observations` | T,S, receipt ID, DB transaction identifier, nullable actual DB commit instant, nullable client acknowledgment instant, observation method/time | PK receipt; additive audit enrichment only; timestamp limits explained in transaction proposal |

The Phase 2 harness supplies stable source tokens and an explicitly ordered sequence. It does not derive identity from text hashes or timestamps, and does not solve actual rotation/capture. Evidence-line numbers used by Phase 1 reports are allocated once per session and retained across retries/restarts; they are not regenerated from a new batch index. Session input adapters preserve original sample line numbers in fixture parity mode.

`normalized_evidence` explicitly stores `(T,S,normalized_evidence_id,receipt_id,raw_evidence_id,version_id,source_timestamp_text,source_offset,source_zone,source_event_at?,normalized_event_at,normalized_utc_ticks,timestamp_quality,message,fields,identifier)`. PK `(T,S,normalized_evidence_id)`; UNIQUE `(T,S,receipt_id)`; same-scope receipt/raw/version FKs. Phase 2 has one normalized entry per successfully parsed logical input; parse failures retain raw evidence/diagnostics without fabricating normalized time. `entry_interpretations` references this row and retains matches/effects; its event/message/identifier data are read from this reference rather than stored as independently editable copies. `run_evidence`, `occurrence_evidence` and `recovery_evidence` retain raw links and add matching normalized-evidence references; constraints verify both identify the same receipt. Multiline framing and continuous normalization workers are deferred.

Every interpreted historical fact has immutable version provenance: runs and normalized evidence reference the version directly; Occurrences reference their origin receipt/run; recoveries reference their success run/receipt; metric facts reference their finalized run/receipt; history identifies its origin. Each later occurrence enrichment has a durable interpretation receipt with its own version. An Incident can span compatible versions, so do not misleadingly label the whole episode with just the currently active version. Its creation version comes from the creation receipt, with later transitions retaining their own provenance. Manual workflow records identify a command/actor, not a fictional parsing version.

## Runs and evidence relationships

One physical `runs` table uses EF discriminator `scope` (`Application` or `Order`), rather than two divergent implementations of `RunRecord`. The conceptual Application Runs and Order Runs are distinct constrained rows/read views. Parent/child metrics intentionally count both rows separately. EF uses storage subtypes with table-per-hierarchy mapping; both reconstruct the existing Domain `RunRecord`.

`runs` columns: T,S, `run_id` text, application ID, P, version ID, stream key, scope, cycle sequence, parent application run ID nullable, identifier nullable, attempt number, lifecycle, result nullable, started event time/ticks, completed event time/ticks nullable, completed processing time/ticks nullable, terminal reason, observed success/failure flags, creation receipt, completion receipt nullable, revision.

- PK `(T,S,run_id)`; UNIQUE application-cycle identity `(T,S,P,stream_key,cycle_sequence)` WHERE scope=Application. Parent has null parent/identifier and attempt=1.
- Logical UNIQUE order attempt `(T,S,parent_application_run_id,exact identifier,attempt_number)` WHERE scope=Order. Implement its index using `identifier_value_id` from `identifier_values(T,S,value_id,exact_text,lookup_digest)`, an immutable exact-value registry with the same collision-safe interning mechanism described below for Problem Identity. A constraint verifies the stored identifier equals the registered value. This avoids indexing arbitrarily long extracted text directly. Parent is mandatory, identifier nonempty, attempt positive; Phase 1 currently produces attempt=1. Persisting an attempt column does not authorize same-cycle retry semantics.
- Composite self-FK includes T,S,P,version,cycle sequence and parent ID. A constraint trigger verifies parent scope Application and identical stream. Order completion never overwrites parent result.
- Running requires null result/completion fields; Finalized requires result in Success/Failure/Undefined, both completion clocks, terminal reason and completion receipt. Finalized interpretation fields cannot be updated. Event times are not constrained to monotonically increase; valid source clocks can differ from processing order.
- `run_evidence(T,S,run_id,evidence_id)` links all associated inputs, UNIQUE on that tuple. `run_problem_links(T,S,run_id,problem_identity_id)` preserves diagnostic associations separately from terminal result. Each evidence ID maps to a stable engine evidence-line number via receipt.

## Problem Identity, Incidents and history

`problem_identities`: T,S, problem UUID, application ID, P, scope, stream key, identifier namespace?, identifier?, condition key, **exact `problem:v1:` canonical IncidentKey text**, lookup digest. Scope checks require both identifier fields for Order and null fields for Application. Validate canonical text against the stored tuple using the versioned domain serialization contract at insertion. No cycle, attempt, severity, version number, message text or timestamp is part of the Problem Identity. Session isolates simulations; it does not alter the domain key displayed in reports.

Identity equality is the full canonical value with ordinal semantics, never digest equality. To avoid PostgreSQL index-size limits for long configured values, use a nonunique fixed-size digest lookup index and an insert trigger/function that takes a transaction advisory lock for that digest bucket, checks exact full-key equality, and returns/rejects the existing exact identity. Bucket collisions only serialize unrelated identities; distinct full keys remain separate. Run this operation under READ COMMITTED, recheck after acquiring the lock, make identity rows immutable, and test simultaneous registration plus forced digest collisions. Revoke bypass insertion paths; the same validation/uniqueness trigger applies to direct inserts. Small technical UUID identity references then support normal unique indexes on incidents. Do not truncate identifiers to fit an index.

| Table | Important columns | Exact identity/constraints |
| --- | --- | --- |
| `incidents` | T,S, domain incident ID, problem UUID, recovery policy, severity Error/Warning, status, created receipt, revision | PK `(T,S,incident_id)`; partial UNIQUE `(T,S,problem_identity_id)` WHERE status IN ('Active','Investigating'); resolved episodes retained; no unique problem key across all historical episodes |
| `incident_occurrences` | T,S, domain occurrence ID, incident ID, run ID, parent run ID, cycle sequence, result nullable, severity, first detected event time/ticks, first receipt | PK occurrence; UNIQUE `(T,S,incident_id,run_id)`; same-target ownership checks; **not one Occurrence per line** |
| `occurrence_evidence` | T,S, occurrence ID, evidence ID | Unique tuple; repeated same-run detection adds evidence and may escalate severity/update its result exactly as Phase 1 does; preserve first detection time |
| `recoveries` | T,S, recovery UUID, incident ID, successful run ID, application run ID, cycle sequence, recovered processing time/ticks, method, receipt ID | UNIQUE `(T,S,incident_id,successful_run_id)`; trigger verifies successful finalized run, same Profile/target/identifier and strictly later cycle than eligible Occurrences under existing NextSuccessfulRun policy |
| `recovery_evidence` | T,S, recovery ID, evidence ID | Unique tuple; recovery does not delete failed Occurrences |
| `incident_status_history` | T,S, history UUID, incident ID, incident revision, from nullable, to, changed processing time/ticks, reason, origin receipt/command ID, actor kind/reference nullable | UNIQUE `(T,S,incident_id,incident_revision)` and origin+incident+transition ordinal; first null→Active, actual changes only; automatic resolution references recovery |
| `workflow_command_receipts` | T,S, command UUID, incident ID, expected revision, payload hash, resulting revision/result | UNIQUE `(T,S,command_id)`; reserved/tested CAS persistence primitive; no public manual workflow or account permissions implemented |

Deferred constraint triggers require each committed status change to have matching history and revision, and each automatic resolution to have its successful recovery. Recovery rows and status history are append-only. An occurrence is not completely immutable while the same run is still accumulating evidence: its result/severity/evidence enrichment is constrained and revisioned, not replaced with duplicate failures. Persist input-level interpretations so that enrichment remains auditable. Incident severity remains Phase 1's maximum severity; do not introduce a new reduction rule.

EF maps explicit `long Revision` with `IsConcurrencyToken()`. Mutation SQL increments revision once per aggregate change and compares expected revision; database triggers reject nonincrementing revisions. Duplicate/no-op requests do not increment it. Do not use `xmin` as a public/domain revision or confuse it with actual commit time. EF's concurrency-token comparison is the mechanism for detecting stale updates. [EF Core concurrency documentation](https://learn.microsoft.com/en-us/ef/core/saving/concurrency).

## Metric facts and derived projections

`run_metric_facts`: T,S, run ID, scope, result, completed event time/ticks, completed processing time/ticks, originating completion receipt, original reporting-context ID, event reporting date, processed reporting date. PK/UNIQUE `(T,S,run_id)`; one canonical first-completion fact for each finalized run. A deferred constraint trigger requires exactly one matching fact for a finalized run and none for a Running run, and checks equality with the finalized run/receipt. Facts are append-only and immutable. Do not create one fact per rebuild or per metric policy version.

Both contribution dimensions derive from this single fact:

- System Health: one evaluated unit per completed Application or Order Run on the **completion event's server-local date**; Success contributes one success; Failure/Undefined contribute zero successes. Thus the mixed fixture is 3/4, not 2/3 and not 1/1.
- `completedOrderRunsProcessedToday`: one unit only for scope Order on the **first completion processing server-local date**. Retries in distinct cycles count as distinct completed logical Order Runs. Five days are D-4 through D inclusive with zero-filled missing buckets.

Historical failure facts remain after Incident recovery/manual status changes. Empty denominator is null; use existing decimal rounding to two places. Queries select a session explicitly and qualify `RunMetricFact.RunId` with session for combined inputs so identical simulator seeds cannot collide in the pure calculator.

The formula remains `successful evaluated runs / total evaluated runs × 100`. Warning and Error have equal negative weight where a run is unsuccessful: severity does not multiply its denominator contribution or impose an extra penalty. Results, not Incident counts or colors, determine the contribution; pending terminal-Success-plus-diagnostic policies remain diagnosed as in Phase 1.

Start with queries over indexed facts `(T,S,event_reporting_date)` and `(T,S,processed_reporting_date,scope)`. If a rebuild demonstration uses stored buckets, keep `metric_projection_generations(T,S,generation_id,reporting_context_id,policy_version,watermark,state)` and `daily_metric_projections(T,S,generation_id,date,successful_count,evaluated_count,completed_order_count)`. Unique generation/date prevents duplicate buckets, not canonical-fact duplication. Rebuild into a fresh generation from a consistent snapshot; atomically publish it only at a verified receipt watermark. Block writers briefly for final catch-up/swap or discard/retry a stale generation; never mix half-old and half-new dates. The original facts and date/context attribution remain available for audit.

An OS reporting-timezone change creates an explicit reporting context and a full new projection generation for the chosen read context. Never silently mix zones or rewrite source/processing instants. Retain original recorded dates and clearly identify which context the rebuilt query uses; live OS-change detection is outside Phase 2.

## Stored domain objects versus reconstruction

| Existing object | Persistence treatment |
| --- | --- |
| Profile/Rule/PatternAlternative | Exact published snapshot plus normalized immutable children; draft separate; reconstruct a defensive copy before interpreter use |
| SampleEntry/ParsedEntry | Raw evidence + processing receipt + interpretation record; source and processing clocks remain separate |
| RunRecord | Persist constrained run row, evidence/problem links and observed flags; restore through Domain state contract, not reflection |
| Incident/Occurrence/RecoveryEvent/StatusChange | Separate durable rows/links; technical IDs supplied for Phase 1 recovery/history records that lack IDs |
| ProblemIdentity | Immutable exact registry value; reconstructed tuple must generate the identical displayed IncidentKey |
| RunMetricFact | Canonical immutable row on first finalization |
| Private cycle/openOrders/counters | Reconstruct from run state and runtime metadata; persist counters, blocked state, ordering and ID allocator explicitly; optional snapshot cache is checked against fact watermark |
| CurrentHealth/Metrics/VolumeBucket | Read models rebuilt from incidents, finalized runs, and facts; never authoritative independently editable columns |
| RuleMatch/ProblemDecision/diagnostics/report | Immutable interpretation/simulation provenance; not an alternative source of outcomes inferred from action strings |

Classification of persistence responsibility: configuration snapshots, run/incident records and metric facts are **persisted domain data** through separate storage types; cycle/open-order associations and aggregate object graphs are **reconstructed state**; health, counters for dashboard display and volume buckets are **derived read models**. Parser/matcher instances, compiled regex, working interpreter clone, EF tracking objects and before/after change sets are **transient processing objects** and are discarded after each attempt. Match/decision/diagnostic values may be copied into immutable audit reports, but executable objects and human-readable Action strings are not authoritative stored state.

Reconstruct current health using the exact engine rule: unresolved Error → Error; otherwise any unresolved Incident → Warning; otherwise any finalized run → Stable; otherwise null/unobserved. Profile summaries use the same rule; application summary considers its Profile lanes collectively. Reader availability and stale-data policy are not inferred here. Rehydrate incident workflow state from durable current row/history, not only from an old checkpoint that could predate a status revision.
